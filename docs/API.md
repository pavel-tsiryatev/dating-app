# CAMPUS API

Один бэкенд для сайта, мобильного приложения и бота. Этот документ — для тех, кто пишет клиент:
как войти, в каком порядке вызывать эндпоинты и какие ошибки обрабатывать.

| Что | Где |
|---|---|
| Интерактивная документация (Swagger) | `http://localhost:3000/docs` при запущенном сервере |
| Полная схема в формате OpenAPI 3 | [`apps/api/openapi.json`](../apps/api/openapi.json) — можно импортировать в Postman или сгенерировать по ней клиент |
| Как запустить сервер | [`README.md`](../README.md) |
| Модель ИС, по которой сделан API | [`CAMPUS_IS_model.pdf`](CAMPUS_IS_model.pdf) |

Все примеры запросов и ответов ниже получены с работающего сервера, а не написаны вручную.
Номера вида «11», «22», «A5» — это задачи дерева и блоки IDEF0 из модели ИС.

## 1. Общие правила

### Формат данных

- Запросы и ответы — JSON в UTF-8, заголовок `Content-Type: application/json`.
- Идентификаторы — UUID (кроме интересов).
- Даты — ISO 8601 в UTC: `2026-11-20T13:00:00.000Z`. В запросах можно указывать смещение: `2026-11-20T18:00:00+05:00`.
- Деньги — целое число **в копейках**: `40000` — это 400 ₽.
- Лишние поля в запросе — ошибка `400`: сервер принимает только описанные поля.

### Вход

Пароля нет. Студент вводит корпоративную почту вуза, получает код из 6 цифр и обменивает его на токен.
Это одновременно регистрация и подтверждение статуса студента (сценарий [С1](#с1-регистрация-и-вход)).

Токен (JWT, действует 7 дней) передаётся в каждом запросе:

```http
Authorization: Bearer <токен>
```

Без токена доступны только `POST /auth/email/request`, `POST /auth/email/verify`, `POST /payments/webhook` и `GET /health`.

Статус пользователя проверяется при каждом запросе. Если модератор заблокировал аккаунт, уже выданный токен
сразу перестаёт работать (ответ `403`).

### Роли

| Роль | Что может |
|---|---|
| `STUDENT` | Всё, кроме эндпоинтов `/admin/*` |
| `MODERATOR` | Дополнительно: очередь жалоб и решения по ним |
| `ADMIN` | Дополнительно: партнёры, мероприятия, отчёт; а также всё, что может модератор |

Роль назначается в базе данных (`users.role`), через API её изменить нельзя.

### Ошибки

Все ошибки приходят в одном формате:

```json
{
  "statusCode": 409,
  "message": "Вы уже оценили эту анкету",
  "error": "Conflict"
}
```

- `message` — готовый текст для пользователя на русском. При ошибке проверки полей (`400`) это **массив строк**.
- `code` — есть только там, где клиент должен отреагировать особым образом. Сейчас один код: `LIKE_LIMIT`.
- `attemptsLeft` — только в ответе `422` на неверный код входа.

| Статус | Когда | Что делать клиенту |
|---|---|---|
| `400` | Ошибка в полях запроса или нарушено правило (например, возраст меньше 18) | Показать `message` |
| `401` | Нет токена, токен истёк или аккаунт удалён | Отправить на экран входа |
| `403` | Аккаунт заблокирован, не хватает роли или это чужая переписка | Показать `message` |
| `404` | Объект не найден или недоступен | Показать `message` |
| `409` | Действие уже выполнено или сейчас невозможно (мест нет, анкета не заполнена) | Показать `message`, обновить данные |
| `422` | Неверный код входа | Показать, сколько попыток осталось (`attemptsLeft`) |
| `429` | Слишком часто: лимит лайков, пауза между кодами, лимит запросов | Подождать; при `code: LIKE_LIMIT` предложить Premium |

Примеры:

Ошибка проверки полей — `message` массивом:
```http
PUT /profile
Authorization: Bearer <токен>
Content-Type: application/json

{
  "name": "Анна",
  "university": "УрФУ",
  "institute": "ИЕНиМ",
  "goal": "DATING",
  "interests": [
    "кино"
  ]
}
```
Ответ `400`:
```json
{
  "message": [
    "Нужно хотя бы 3 интереса"
  ],
  "error": "Bad Request",
  "statusCode": 400
}
```

Запрос без токена:
```http
GET /profile
```
Ответ `401`:
```json
{
  "message": "Нужен вход",
  "error": "Unauthorized",
  "statusCode": 401
}
```

Не хватает роли:
```http
GET /admin/reports
Authorization: Bearer <токен>
```
Ответ `403`:
```json
{
  "message": "Недостаточно прав",
  "error": "Forbidden",
  "statusCode": 403
}
```

### Лимиты

| Что | Лимит |
|---|---|
| Любые запросы с одного IP | 120 в минуту |
| Запрос кода (`/auth/email/request`) с одного IP | 5 в минуту |
| Проверка кода (`/auth/email/verify`) с одного IP | 10 в минуту |
| Новый код на одну и ту же почту | не чаще раза в минуту |
| Неверные попытки ввода кода | 3, затем почта блокируется на 15 минут |
| Срок действия кода | 10 минут |
| Лайки без Premium | 30 в сутки (сутки считаются по Екатеринбургу, UTC+5) |
| Фото в анкете | до 6 |
| Интересы в анкете | от 3 до 10 |
| Бронь места на мероприятии | 30 минут |

## 2. Сценарии

Сценарии соответствуют разделу 3 модели ИС (С1–С7).

### С1. Регистрация и вход

**Шаг 1.** Запросить код. Почта должна быть в домене вуза.

```http
POST /auth/email/request
Content-Type: application/json

{
  "email": "anna@urfu.me"
}
```
Ответ `202`:
```json
{
  "sent": true
}
```

В разработке, пока не настроен SMTP, код не отправляется письмом, а выводится в лог сервера: `Код для anna@urfu.me: 123456`.

Если почта не вузовская:
```http
POST /auth/email/request
Content-Type: application/json

{
  "email": "ivan@gmail.com"
}
```
Ответ `400`:
```json
{
  "message": "Нужна корпоративная почта вуза",
  "error": "Bad Request",
  "statusCode": 400
}
```

Если код запросили повторно раньше чем через минуту:
```http
POST /auth/email/request
Content-Type: application/json

{
  "email": "wrong@urfu.me"
}
```
Ответ `429`:
```json
{
  "statusCode": 429,
  "message": "Код уже отправлен. Запросить новый можно через минуту"
}
```

**Шаг 2.** Обменять код на токен. При первом входе обязательны `birthDate` (только 18+) и `acceptTerms: true` —
согласие на обработку персональных данных. При следующих входах достаточно `email` и `code`.

```http
POST /auth/email/verify
Content-Type: application/json

{
  "email": "anna@urfu.me",
  "code": "123456",
  "birthDate": "2005-04-17",
  "acceptTerms": true
}
```
Ответ `200`: `isNew: true` значит, что пользователь только что создан и нужно показать экран анкеты.
```json
{
  "accessToken": "eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9…",
  "isNew": true
}
```

Неверный код:
```http
POST /auth/email/verify
Content-Type: application/json

{
  "email": "wrong@urfu.me",
  "code": "000000"
}
```
Ответ `422`:
```json
{
  "statusCode": 422,
  "message": "Неверный код",
  "attemptsLeft": 2
}
```

Если при первом входе не хватило даты рождения или согласия, сервер ответит `400`, но код не «сгорит»:
запрос можно повторить с тем же кодом. После успешного входа код использовать второй раз нельзя.

**Шаг 3.** Заполнить анкету. Запрос заменяет анкету целиком.

```http
PUT /profile
Authorization: Bearer <токен>
Content-Type: application/json

{
  "name": "Анна",
  "university": "УрФУ",
  "institute": "ИЕНиМ",
  "goal": "DATING",
  "about": "Люблю настолки и походы",
  "interests": [
    "настолки",
    "кино",
    "бег"
  ],
  "hideFromInstitute": false
}
```
Ответ `200`:
```json
{
  "id": "85b5f31a-a733-4098-8b16-661c62846926",
  "universityEmail": "anna@urfu.me",
  "isVerified": true,
  "birthDate": "2005-04-17T00:00:00.000Z",
  "role": "STUDENT",
  "status": "ACTIVE",
  "profile": {
    "userId": "85b5f31a-a733-4098-8b16-661c62846926",
    "name": "Анна",
    "university": "УрФУ",
    "institute": "ИЕНиМ",
    "goal": "DATING",
    "about": "Люблю настолки и походы",
    "hideFromInstitute": false,
    "photos": [],
    "interests": [
      "настолки",
      "кино",
      "бег"
    ]
  }
}
```

**Шаг 4.** Добавить хотя бы одно фото — без него анкета не попадёт в ленту.

```http
POST /profile/photos
Authorization: Bearer <токен>
Content-Type: application/json

{
  "storageKey": "photos/anna/1.jpg"
}
```
Ответ `201`:
```json
{
  "id": "0c1f423c-ab61-4c53-857b-44effb0412d3",
  "userId": "85b5f31a-a733-4098-8b16-661c62846926",
  "storageKey": "photos/anna/1.jpg",
  "position": 0
}
```

> Сейчас эндпоинт принимает ключ уже загруженного файла. Выдача ссылки для загрузки в хранилище появится
> при подключении S3 — см. «Что ещё не сделано» в [`apps/api/README.md`](../apps/api/README.md).

Свои данные в любой момент: `GET /profile`. Пока анкета не заполнена, `profile` равен `null`.

**Шаг 2.** Оценить анкету: `isLike: true` — лайк, `false` — пропустить. Оценённая анкета больше не появится в ленте.

```http
POST /likes
Authorization: Bearer <токен>
Content-Type: application/json

{
  "toUserId": "85b5f31a-a733-4098-8b16-661c62846926",
  "isLike": true
}
```
Ответ `201`: Лайк пока не взаимный.
```json
{
  "match": false,
  "matchId": null
}
```

Когда второй человек ставит лайк в ответ, создаётся совпадение:

```http
POST /likes
Authorization: Bearer <токен>
Content-Type: application/json

{
  "toUserId": "ba88f005-dd6d-4292-8fc9-f1da77379b26",
  "isLike": true
}
```
Ответ `201`: `matchId` нужен для переписки.
```json
{
  "match": true,
  "matchId": "2b00eb18-d9ba-40e8-9f92-decd4af2fad9"
}
```

Повторная оценка той же анкеты:
```http
POST /likes
Authorization: Bearer <токен>
Content-Type: application/json

{
  "toUserId": "ba88f005-dd6d-4292-8fc9-f1da77379b26",
  "isLike": true
}
```
Ответ `409`:
```json
{
  "message": "Вы уже оценили эту анкету",
  "error": "Conflict",
  "statusCode": 409
}
```

Когда бесплатный лимит исчерпан, лайк возвращает `429` с `code: "LIKE_LIMIT"` — это сигнал предложить Premium (С6):

```json
{
  "statusCode": 429,
  "message": "Лимит лайков на сегодня исчерпан",
  "code": "LIKE_LIMIT"
}
```

**Шаг 3.** Переписка. `clientId` придумывает клиент (любая уникальная строка в пределах переписки).
Если связь оборвалась и неясно, дошло ли сообщение, повторите запрос **с тем же `clientId`** — дубля не будет.

```http
Authorization: Bearer <токен>
Content-Type: application/json

{
  "clientId": "c7d1-1",
```

### С3. Жалоба и модерация

Студент жалуется на другого пользователя. Одна жалоба на одного человека.

```http
POST /reports
Authorization: Bearer <токен>
Content-Type: application/json

{
  "targetId": "b536ea66-ee73-432e-b3d4-e38ecd470c99",
  "reason": "Оскорбления в переписке"
}
```
Ответ `201`:
```json
{
  "id": "d3e83740-60c5-4a48-bf30-eff5079908e0",
  "status": "OPEN"
}
```

Когда на одного человека есть 3 открытые жалобы от разных людей, его статус становится `HIDDEN`:
анкета пропадает из ленты до решения модератора. Сам пользователь продолжает пользоваться сервисом и видит статус в `GET /profile`:

```http
GET /profile
Authorization: Bearer <токен>
```
Ответ `200`: (ответ сокращён)
```json
{
  "id": "b536ea66-ee73-432e-b3d4-e38ecd470c99",
  "universityEmail": "egor@urfu.me",
  "isVerified": true,
  "role": "STUDENT",
```

### С5. Покупка билета

Билет покупается в три шага: бронь → платёж → подтверждение от платёжного сервиса.

**Шаг 1.** Забронировать место. Бронь держится 30 минут (`reservedUntil`).

```http
POST /events/9a8d5376-d40c-47f3-886c-c02476824644/tickets
Authorization: Bearer <токен>
```
Ответ `201`:
```json
{
  "eventId": "9a8d5376-d40c-47f3-886c-c02476824644",
  "userId": "ba88f005-dd6d-4292-8fc9-f1da77379b26",
  "paymentId": null,
  "status": "RESERVED",
  "reservedUntil": "2026-11-12T13:58:16.730Z"
}
```

Если мест нет:
```http
POST /events/9a8d5376-d40c-47f3-886c-c02476824644/tickets
Authorization: Bearer <токен>
```
Ответ `409`:
```json
{
  "message": "Мест нет",
  "error": "Conflict",
  "statusCode": 409
}
```

**Шаг 2.** Создать платёж и отправить студента по ссылке `confirmationUrl`.

Заголовок `Idempotency-Key` необязателен, но полезен: если запрос повторится (двойное нажатие, обрыв связи),
вернётся тот же платёж с той же ссылкой, второй не создастся. То же самое произойдёт и без ключа, пока по брони есть неоплаченный платёж.

```http
POST /payments
Authorization: Bearer <токен>
Idempotency-Key: ticket-boris-1
Content-Type: application/json

{
  "kind": "TICKET",
  "eventId": "9a8d5376-d40c-47f3-886c-c02476824644"
}
```
Ответ `201`:
```json
{
  "id": "caf8686c-c798-4fda-a970-400045a27489",
  "kind": "TICKET",
  "amount": 40000,
  "status": "PENDING",
  "idempotencyKey": "ticket-boris-1",
  "confirmationUrl": "https://pay.example.test/checkout/fake_caf8686c-c798-4fda-a970-400045a27489"
}
```

**Шаг 3.** Платёжный сервис сам сообщает серверу о результате — клиент этот запрос не делает.
Статус билета меняется **только** этим уведомлением, а не возвратом студента со страницы оплаты.

В учебной версии платёжный сервис заменён заглушкой, и уведомление можно отправить вручную,
указав секрет из переменной `PAYMENT_WEBHOOK_SECRET`:

```http
POST /payments/webhook
X-Webhook-Secret: <PAYMENT_WEBHOOK_SECRET>
Content-Type: application/json

{
  "providerPaymentId": "fake_caf8686c-c798-4fda-a970-400045a27489",
  "status": "succeeded"
}
```
Ответ `200`:
```json
{
  "ok": true,
  "duplicate": false
}
```

Повторное уведомление о том же платеже ничего не меняет:

```json
{
  "ok": true,
  "duplicate": true
}
```

С неверным секретом:

```json
{
  "message": "Неверная подпись уведомления",
  "error": "Unauthorized",
  "statusCode": 401
}
```

**Шаг 4.** Клиент проверяет результат в списке своих билетов: статус `PAID` — билет оплачен.

```http
GET /tickets
Authorization: Bearer <токен>
```
Ответ `200`:
```json
[
  {
    "eventId": "9a8d5376-d40c-47f3-886c-c02476824644",
    "userId": "ba88f005-dd6d-4292-8fc9-f1da77379b26",
    "paymentId": "caf8686c-c798-4fda-a970-400045a27489",
    "status": "PAID",
    "reservedUntil": "2026-11-12T13:58:16.730Z",
    "event": {
      "id": "9a8d5376-d40c-47f3-886c-c02476824644",
      "partnerId": "561ab75d-4eaf-4c04-acdd-8b26c31b50f7",
      "title": "Вечер настолок",
      "startsAt": "2026-11-22T14:00:00.000Z",
      "capacity": 1,
      "price": 40000
    }
  }
]
```

Если студент не оплатил за 30 минут, таймер на сервере (раз в 5 минут) переводит бронь в `RELEASED`
и место освобождается. Записаться можно заново тем же запросом из шага 1.

## 3. Справочник эндпоинтов

Раздел собран из [`openapi.json`](../apps/api/openapi.json). Жирным выделены обязательные поля.
Ошибки `401`, `403` и `429` из раздела [«Ошибки»](#ошибки) возможны у всех эндпоинтов, требующих входа, и ниже не повторяются.

### A1 · Пользователи

#### `POST /auth/email/request`

11–12: отправить код на почту вуза. Без входа. Код из 6 цифр действует 10 минут. Без настроенного SMTP код выводится в лог сервера.

Тело запроса:

| Поле | Тип | Описание |
|---|---|---|
| **`email`** | строка | Пример: `ivan.petrov@urfu.me` |

Ответ: `202` — [`CodeSentDto`](#codesentdto)

| Ошибка | Когда |
|---|---|
| `400` | Почта не в домене вуза или неверный формат |
| `403` | Аккаунт заблокирован |
| `429` | Код уже отправлен (пауза 1 минута), почта заблокирована после 3 ошибок (15 минут) или больше 5 запросов в минуту с одного адреса |

#### `POST /auth/email/verify`

11–12: проверить код → токен. Без входа. При первом входе регистрирует пользователя: нужны birthDate (18+) и acceptTerms: true. Если их не хватило, запрос можно повторить с тем же кодом.

Тело запроса:

| Поле | Тип | Описание |
|---|---|---|
| **`email`** | строка | Пример: `ivan.petrov@urfu.me` |
| **`code`** | строка | Пример: `123456` |
| `birthDate` | строка | Обязательна при первом входе (проверка 18+) Пример: `2005-04-17` |
| `acceptTerms` | да/нет | Согласие на обработку персональных данных. Обязательно при первом входе |

Ответ: `200` — [`TokenDto`](#tokendto)

| Ошибка | Когда |
|---|---|
| `400` | Код истёк, не запрашивался или уже использован; при регистрации — нет согласия, нет даты рождения или возраст меньше 18 |
| `403` | Аккаунт заблокирован |
| `422` | Неверный код. В ответе attemptsLeft — сколько попыток осталось |
| `429` | Попытки закончились: почта заблокирована на 15 минут |

## 4. Значения перечислений

| Перечисление | Значение | Смысл |

| Роль (`role`) | `STUDENT` | Студент |

| | `DECLINED` | Отклонена |

| | `CLOSED` | Рассмотрена |

| | `WARNED` | Предупреждение |

## 5. Как обновлять документацию

Описание эндпоинтов живёт в коде, рядом с самими эндпоинтами (декораторы `@ApiOperation`, `@ApiErrors`
и классы ответов в папках `dto`). После изменения API:

```bash
cd apps/api
pnpm openapi      # пересобрать openapi.json (база и Redis не нужны)
pnpm test:e2e     # тест упадёт, если openapi.json разошёлся с кодом
```

Разделы 1, 2 и 4 этого файла правятся вручную. Раздел 3 повторяет `openapi.json`: если они разошлись, верным считается `openapi.json`.
