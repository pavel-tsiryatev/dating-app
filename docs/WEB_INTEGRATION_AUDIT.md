## 3. Исправленные ошибки

| Ошибка до исправления | Что изменено / как проверено |
|---|---|
| Лайк по известному userId мог обходить часть правил видимости ленты | Проверяется скрытие анкеты, институт, фото, интересы и личные блокировки. Прямой лайк скрытой анкеты получает 404 |
| `кино`, `Кино`, ` кино ` могли пройти как три интереса | Проверка выполняется после trim, lowercase и удаления дублей; такой запрос получает 400 |
| Параллельная загрузка могла превысить 6 фото | Изменение сериализовано блокировкой строки профиля. Проверка 8 конкурентных запросов оставляет ровно допустимое число фото |
| Изменение порядка фото могло нарушить уникальность позиции | Позиции меняются в одной транзакции через временный диапазон; чужие и повторяющиеся ID отклоняются |
| Загруженные файлы оставались после удаления фотографии | Файл удаляется после удаления записи, если других ссылок на него нет; e2e подтверждает 404 после удаления |
| Два ответа на встречу могли перезаписать друг друга | Условное атомарное обновление только из `PROPOSED`: конкурентные ответы дают 200 и 409 |
| Карточки встреч зависели от JSON в тексте сообщений | В обычном режиме встречи и их статусы читаются отдельным методом из базы; принятие вторым участником обновляет карточку первого |
| Собеседник мог переиспользовать чужой `clientId` | Проверка автора до и после идемпотентного upsert; конфликт возвращает 409 |
| Конкурентные лайки могли превысить дневной лимит | Лимит повторно проверяется под блокировкой пользователя внутри транзакции; при 29 лайках два запроса дают 201 и 429, итог — 30 |
| Два платежа на одну бронь могли создаваться параллельно | Бронь блокируется на время создания; два разных ключа для одной ожидающей оплаты возвращают один платёж |
| Один ключ идемпотентности мог вернуть другой тип заказа | Проверяются пользователь, тип и событие; несовместимый повтор получает 409 |
| Поздняя оплата могла переполнить событие или оживить отменённую бронь | Callback заново проверяет привязку билета, занятость и вместимость под блокировками; отмена снимает привязку платежа. Регрессия последнего места проверена |
| Успешный платёж мог показываться как выданный билет, хотя билет не выдан | API возвращает `requiresRefund`; интерфейс показывает отдельное состояние сверки/возврата |
| Ссылка fake-провайдера вела на несуществующий домен | Добавлена рабочая локальная песочница; webhook-секрет остаётся на сервере. Реального списания денег нет |
| Проверка статуса использовала повторное создание платежа | Фронтенд использует `GET /payments/:id`, восстанавливает заказ после перезагрузки |
| Открытие оплаты после асинхронного запроса могло блокироваться браузером | Создание заказа и пользовательский переход по ссылке разделены; локальная песочница открывается в той же вкладке и сохраняет sessionStorage |
| Анкеты и события частично использовали временные списки | Подключены серверные исходящие симпатии, фильтры, категории, постеры, редактор и черновики |
| Перезагрузка теряла выбранный чат и билет | Идентификаторы сохраняются в сессии; чат, встречи и оплаченный QR-билет восстанавливаются |
| Данные предыдущего аккаунта могли оставаться в памяти после переключения режима | Выход и переход в деморежим очищают дополнительные персональные состояния |
| Таймер повторной отправки показывал `00:60` | Исправлен формат на `01:00` |
| Статистика принимала обратный или чрезмерный диапазон дат | Проверяется порядок дат и ограничение 366 дней; некорректные запросы получают 400 |

## 6. Проверки в браузере через Playwright

Проверены обычный режим и два отдельных локальных аккаунта:

1. Запрос кода через фронтенд, чтение кода из development-лога API, реальный вход и получение ленты из PostgreSQL.
2. Пропуски двух анкет и взаимный лайк с третьей; запись сообщения через API.
3. Создание встречи первым участником, принятие вторым; автоматическое обновление статуса у первого.
4. Перезагрузка страницы чата: сообщение и встреча восстанавливаются из базы.
5. Бронирование события, создание платежа, переход в локальную песочницу, callback, проверка статуса и выдача настоящего QR.
6. Перезагрузка страницы оплаченного билета: QR остаётся доступным.
7. Выбор файла с устройства, multipart-загрузка, смена обложки, перезагрузка и проверка сохранённого `/api/media/...` изображения.
8. Редактирование события и сохранение в базу; статистика по дням; сохранение темы и проверка после перезагрузки.

Отдельно проверен рендер всех **42 экранов в деморежиме** в iframe с настоящим viewport 390 px. Горизонтального переполнения и ошибок JavaScript не обнаружено. Это проверка вёрстки, а не утверждение о прохождении всех 42 бизнес-сценариев в production.

## 7. Что остаётся ограничением

- **Реальных платежей и автоматических возвратов нет.** Работает проверенная локальная песочница. Поздняя успешная оплата без билета требует ручной сверки/возврата; интерфейс сообщает об этом. Неизвестный платёжный провайдер теперь отклоняется конфигурацией, а не молча подменяется fake.
- **SMTP и push не настроены.** Код входа выводится в development-лог; настройка уведомлений сохраняется и учитывается сервером, но внешняя доставка push ещё не реализована.
- **Хранилище фотографий локальное.** Нет S3/CDN, антивирусной обработки и пересоздания изображений. Проверяются размер и сигнатура; URL медиа публичный по случайному имени. Файлы нужно включать в резервное копирование отдельно от БД.
- QR проверен API с однократным входом. В интерфейсе команды реализован ввод считанного кода; доступ к камере / встроенный видеосканер не добавлялись.
- Это аудит интеграции и конкретных регрессий, а не полный security-аудит, нагрузочный тест или проверка production-инфраструктуры. Юридические тексты учебного проекта не заменены утверждённой политикой оператора.
