# CAMPUS — аудит проекта и план по трём клиентам

Дата: 12 ноября 2026. Состояние: `main` (бэкенд + веб-клиент) слит с веткой документации API
(`ccr-f190219b-gbxvqb`).

Цель аудита — понять, что из текущего кода годится для трёх вариантов клиента (**сайт**, **мобильное
приложение**, **Telegram**) и что нужно доделать в бэкенде, чтобы все три работали на нём без форков.

## 1. Итог

- **Бэкенд в хорошем состоянии.** Бизнес-правила (18+, почта вуза, лимит лайков, брони, идемпотентные платежи,
  модерация) закрыты транзакциями и блокировками, покрыты 7 юнит- и 37 e2e-тестами на настоящих PostgreSQL и Redis.
  Бэкенд уже клиент-нейтральный: REST + JWT в заголовке, без cookie и серверного рендера. Это правильная основа
  для трёх клиентов.
- **Сайт (`frontend/web`) работает** со всеми сценариями, но написан без фреймворка: 77 КБ JS в 187 строках
  (сжатый стиль), разметка через `innerHTML`. Для веба и Telegram Mini App подходит; в мобильное приложение
  код не переносится — переиспользовать можно только контракт API и дизайн.
- **Главные пробелы для мобильного приложения и Telegram — в бэкенде:** нет refresh-токенов, push/Telegram-
  уведомлений, real-time для чата, входа через Telegram, а лимит запросов считается по IP. Ниже — список
  с приоритетами.

## 2. Бэкенд

### Сильные стороны

- Вход по коду на почту вуза: хеш кода в Redis, одноразовость через атомарный `DEL`, лимит попыток через `INCR`,
  блокировка на 15 минут, `timingSafeEqual`. Код в логи не попадает (кроме режима без SMTP).
- `AuthGuard` читает статус пользователя из базы на каждый запрос — блокировка модератором действует сразу.
- Гонки закрыты: лимит лайков, последнее место на событии, поздняя оплата, двойной ответ на встречу,
  порядок фото — всё под блокировками строк, с тестами на конкурентные запросы.
- Платежи: идемпотентность по ключу и по брони, webhook повторно проверяет вместимость; `requiresRefund`
  честно показывает случай «деньги пришли, билет выдать нельзя».
- Конфигурация проверяется при старте; в production запрещены короткий `JWT_SECRET`, пустой `CORS_ORIGIN`
  и выключенный лимит запросов.
- Удаление аккаунта (152-ФЗ) каскадно удаляет данные и файлы фото.

### Проблемы и риски

| # | Приоритет | Проблема | Что сделать |
|---|---|---|---|
| B1 | Высокий | **Нет refresh-токенов и отзыва сессий.** JWT живёт 7 дней, «выход» только стирает токен на клиенте; украденный токен действует до истечения | Короткий access (15 мин) + refresh-токен в таблице `sessions` (устройство, клиент: web/ios/android/telegram), `POST /auth/refresh`, `POST /auth/logout`. Нужно всем трём клиентам, мобильному — обязательно |
| B2 | Высокий | **Уведомлений нет**: `NotificationsService` только пишет в лог | Каналы: Expo Push (таблица push-токенов), Telegram (`telegramId`), e-mail для важного. Отправка через очередь (BullMQ на уже имеющемся Redis), чтобы падение внешнего сервиса не ломало запрос |
| B3 | Высокий | **Чат только опросом** (каждые 5 с): нагрузка растёт линейно с числом открытых чатов, на телефоне садит батарею | SSE или WebSocket (`@nestjs/websockets`) с Redis pub/sub; опрос оставить как запасной вариант |

## 4. Мобильное приложение — `frontend/mobile`

Кода пока нет. Рекомендация: **Expo (React Native) + TypeScript**, клиент API генерируется из `openapi.json`.

Блокеры в бэкенде: **B1** (refresh-токены), **B2** (push), **B3** (real-time), **B5** (фото), **B6** (deep link
возврата из оплаты).

Особенности:

- Адреса фото относительные (`/api/media/…`) — приложению нужен базовый URL API.
- Хранение токена — `expo-secure-store`.
- **Магазины приложений.** Для приложения знакомств App Store и Google Play требуют жалобы и блокировки
  (есть) и удаление аккаунта из приложения (есть). Premium — цифровая подписка; по правилам магазинов такие
  покупки обычно должны идти через встроенные покупки (IAP), тогда как билеты на офлайн-события — нет.
  Это влияет на `PaymentProvider` и на экономику Premium; проверить актуальные правила и доступность
  оплаты для России до разработки экрана Premium.

## 5. Telegram — `frontend/telegram`

Кода пока нет. Рекомендация: **бот + Mini App**, где Mini App — это сайт из `frontend/web`, открытый в Telegram.
Так лента, чат и билеты не пишутся второй раз, а бот остаётся тонким: вход, уведомления, кнопка «Открыть».

Нужно в бэкенде:

1. **Вход через Telegram:** `POST /auth/telegram` — проверка подписи `initData` (HMAC от токена бота) и срока
   `auth_date`. Первый раз — подтверждение почты вуза кодом, затем `telegramId` привязывается к аккаунту
   (поле в схеме уже есть). Без подтверждённой почты аккаунт не создаётся — правило «только студенты» сохраняется.
2. **Уведомления в Telegram** — канал в `NotificationsService` (B2). Учитывать, что пользователь может
   заблокировать бота (ошибка 403 от Telegram → не слать дальше).
3. **Лимиты** (B4): если бот вызывает API за пользователей, лимит по IP сделает бота неработоспособным
   уже при десятках пользователей.
4. **Оплата:** по правилам Telegram цифровые товары и услуги (Premium) в боте и Mini App продаются за
   Telegram Stars; билеты на офлайн-события можно продавать через обычного провайдера. Значит, для Telegram
   нужен второй `PaymentProvider` или Premium вне Telegram.

## 6. Общий план

Порядок, при котором все три варианта можно пробовать параллельно:

1. **Контракт.** Описать DTO ответов для методов `extensions/` (B7), сгенерировать типизированный клиент
   из `openapi.json` в общий пакет `frontend/shared` — его подключат сайт, приложение и Mini App.
2. **Сессии (B1)** и **лимит по пользователю (B4)** — нужны всем.
3. **Уведомления (B2)** с каналами push и Telegram, затем **real-time чат (B3)**.
4. Клиенты:
   - сайт — уже работает, можно показывать;
   - Telegram — быстрее всего: Mini App = сайт, плюс бот на ~5 команд и `POST /auth/telegram`;
   - мобильное приложение — дольше всего: экраны пишутся заново.
5. Перед реальным запуском: ЮKassa (B6), S3 и удаление EXIF (B5), наблюдаемость (B11), Docker (B10).
